## Checkpoint 5.0: audit and baseline

The original `RegistrationPanel` puts every registry operation in a single method combo, followed by a generic `TaskDialog`. The default view exposes transform import, raw typed-task JSON, output, threads, exact commands, approval and QC together. It does not lead a researcher from an intended goal to moving/fixed images and a compatible method. `RegistrationView` already offers Overlay, Outlines, Checkerboard, Registered Only, Reference Only, blink, categorical atlas region visibility, immutable review and report export. Batch has registration workflow/QC entry points but its native product-to-Viewer integration is not fully verified.

Core `prepare_registration` is the authoritative planner and command gate. The registry has `registration.reference` (first or mean selected low-b), `registration.qc`, `registration.flirt` (rigid/affine), `registration.epi_reg`, `registration.fnirt`, invert, compose, convert, and scalar/labels/ROI/probability apply variants. FNIRT, inversion, composition, conversion and imported transforms have distinct convention and input restrictions. FSL FLIRT matrices are tied to source/reference images; MRtrix and FSL warp conventions differ. The core checks exact spatial associations, correction history, tool versions, executable/source hashes, new output directories, categorical interpolation and plan digest. Unsupported ANTs binary/composite and unverified nonlinear transports remain blocked. This audit is source inspection, not new anatomical acceptance.

Baseline in the restricted local session: `PYTHONPATH=src QT_QPA_PLATFORM=offscreen OPENBLAS_NUM_THREADS=1 ../application/.venv/bin/python -m pytest -q tests/test_registration.py tests/gui/test_scientific_planning.py -k 'not scientific_routes_independent_and_preserve_scene' --tb=short` returned **19 passed, 1 deselected in 16.04 s**. `tests/gui/test_registration_gui.py` contains native VTK/installed-tool tests and was not run offscreen as a substitute for Cocoa. Three separate warm-cache offscreen `scripts/benchmark_gui_performance.py` processes on the local Apple ARM64 Mac measured Registration first-open median **32.145 ms (32.014–32.191)** and return median **33.367 ms (33.269–33.989)** in the benchmark's normal navigation sequence. Batch first/return medians were **93.767/19.823 ms**; Tractography first/return medians **46.894/33.041 ms**. These are not native cold-start or loaded-data measurements.

## Checkpoints 5.1–5.3: guided tasks and exact planning

`RegistrationPanel` now starts with five separate researcher goals: create a diffusion reference, align diffusion/EPI with T1, align two images, move an atlas or ROI, and inspect existing evidence. The applicable inputs and method controls are shown on one task page at a time. The form names moving and fixed images, shows the direction, explains each goal and provides missing-input guidance. It selects compatible imported candidates but delegates final eligibility to the core. The low-b form exposes the actual first/mean selection and threshold; EPI/T1 exposes the required T1 brain image and WM segmentation; image alignment exposes rigid/affine and the supported cost choices; derivative movement maps atlas labels, binary ROIs, scalar anatomy and probability maps to the corresponding existing registry operations. No transform inverse or chain is guessed.

The guided form creates the original typed `Task` and invokes the existing asynchronous `prepare_registration`, `execute_plan` and plan digest approval. Exact commands, scientific limitations and approval digest remain visible. A change to the goal, input, method, output or resources invalidates the draft plan. Ordinary navigation does not recreate the Registration panel. The shared page header now describes Registration instead of unrelated DTI/CSD tasks, and the form fits the 960×640 viewport without horizontal scrolling. The former specialist controls, including FNIRT, inversion, composition, conversion, explicit transform import and typed task configuration, remain under **Advanced Registration Tools**. An explicitly assigned advanced task is preserved by preview; a cross-phase regression test caught and verified that compatibility fix.

## Checkpoints 5.4–5.5: inspection, review and Batch handoff

Direct registration products now open only from a technically validated manifest with unchanged inputs. A generated low-b NIfTI has an image Viewer route. Atlas labels and ROI masks carry categorical display semantics into the existing Viewer, including when a historical Batch attempt is inspected through `inspect_run`; the original source and expected output/reference hashes remain bound to the saved record. The Viewer still verifies the product and reference hashes and overlay grid before display. Overlay, Outlines, Checkerboard, Registered Only, Reference Only and Blink use the existing linked image views; the first five modes now have short explanations. Formal review and QC report controls become available only for a verified registered-atlas QC bundle. A generic alignment can be inspected but is not presented as formally anatomically approved. Batch's existing seven-step results, registration QC table and verified-product route remain in place.

## Performance

Three comparable warm-cache offscreen processes after `5c30ded` measured Registration first-open median **58.175 ms (58.057–58.265)** and return median **50.819 ms (50.542–51.011)**. The Phase 5.0 offscreen baseline was **32.145 ms (32.014–32.191)** first and **33.367 ms (33.269–33.989)** return. The guided UI and task-specific page header therefore add **26.030 ms first** and **17.452 ms return** under these conditions. The panel instance is reused; changed layout/text work is a plausible contributor, but the exact callback costs have not been separated. This is a measurable navigation regression, though the resulting times remain below the 200 ms target. Batch first/return post-change medians were **95.728/20.542 ms**, versus **93.767/19.823 ms** baseline. Tractography was **47.974/34.000 ms**, versus **46.894/33.041 ms** baseline. The final run showed 1,000-row Batch initial rendering **33.931–34.773 ms** and unchanged journal refresh **0.026–0.057 ms** after first read. A 960×640 offscreen light/dark layout check found and fixed a 36-pixel horizontal scrollbar; the final Registration panel has zero horizontal scroll at that size. One earlier offscreen process with a tiny generated NIfTI loaded measured Registration **52.331/50.256 ms** first/return and loading **794.270 ms**, before the last page-header change, so it is not the final loaded-data result.

The user's normal-Terminal Cocoa benchmark at `5c30ded` measured **51.971 ms first** and **34.553 ms return** for empty Registration; with a small synthetic NIfTI loaded, **51.371/34.762 ms** and **417.078 ms** to load. The empty native script-to-interactive sample was **952.131 ms**; the loaded sample was **931.002 ms**. Both were warm-cache script timings, excluding interpreter and disk cold start, and `vtkmodules_loaded` was false during the benchmark. They are single runs per state, not medians or true native cold-start measurements. Native 1,000-row Batch initial rendering was **36.749 ms** empty / **48.369 ms** loaded, and unchanged journal refresh was **0.018 ms** after the first read in both samples; inactive Batch timer ticks were zero. Actual MRI/tractography-loaded Viewer performance and native file-picker timing remain tracked elsewhere in the backlog.

## Handoff

The task-first Registration flow, typed planning, exact approval, advanced operations, verified Viewer handoff and targeted native Batch QC route are implemented and tested. A Phase 6 non-Viewer usability branch can begin from this checkpoint while the 38 scientific/release tasks remain open. Do not treat these synthetic runs as anatomical acceptance or a release gate. Next scientific verification needs reviewed real diffusion/T1/atlas data, independent transform comparisons, missing/rejected/stale Batch QC cases, broader output types, and researcher usability review. True cold start and loaded Viewer performance remain separate measurements. Keep the Phase 1–4 branches, public `main`, releases and scientific algorithms unchanged.
